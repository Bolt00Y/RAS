## 一、工作定位与个人贡献

### 1. 用一分钟讲清楚，你实习期间到底做了什么？

我主要做搜索精排场景下的首次转化率预估，重点是把 RankMixer 接入现有训练框架，并针对早期版本 AUC 低于基线的问题持续改进。

我先从已有模型整理出三桶特征、首次转化任务的 Base，再围绕字段分组、Token 交互、读出方式、归一化和模型宽深做实验。前期探索范围比较大，后期主要集中在 v6 系列，把问题逐步拆到具体结构上。

当前的 Small-3 在两层 Small 上增加一层交互，五个共同测试日都取得了提高，平均 AUC 提升 0.0001892；相比更宽的 E2，它用更少的 Dense 参数获得了更高的五日平均 AUC。不过，它还没有超过 Base，所以我会把这段工作定位为有明确改进和实验积累的阶段性研究，继续优化的目标也很清楚。

### 2. 哪些是你做的，哪些是论文、原有代码和公司成熟方案已经有的？

RankMixer 的基础思想不是我提出的，Base 中的 BN、SENet 和 DCNM 也来自已有模型。我的工作是把这些基础结构落实到当前搜索 CVR 任务，完成输入和任务适配，并围绕实际效果设计、实现和比较不同方案。

具体来说，我做了从完整字段切分到固定语义分组的调整，探索了 Local 和 Global Token、不同交互路径和读出方式，并在 v6 系列中继续比较归一化、宽度和深度。配套还包括字段映射检查、训练配置、参数量核算和实验整理。

代码中带 mature 的版本来自公司线上成熟 RankMixer，我做的是缩参和适配。这部分可以作为学习和工程工作的说明，但成熟架构及其超过 Base 的结果不属于我的模型创新成果。

**追问：那你有什么“创新”？**

我更愿意用“针对当前任务的设计和验证”来描述。可以具体讨论我为什么这样分组、为什么保留完整读出、怎样调整容量，以及结果是否支持这些选择。当前证据还不足以把它上升为一个普遍有效的新算法。

### 3. 你的 Base 是自己搭出来的吗？为什么要改原来的模型？

Base 是从 `cvr_fst_last_norpy.py` 改编的，不是从零设计。我的主要调整是整理当前对照要使用的 common、item、creative 三桶输入，去掉该对照中不用的数值、DIN 序列和 gattr 路径，并为相关预测分支增加开关，便于按首次转化任务配置。

保留下来的分桶 BN、分层 SENet、两层 DCNM 和任务头都有原模型的基础。这样做是为了让后续比较集中在同一组输入上的 Dense 建模差异，避免一边换结构、一边又增加特征或改变任务，最后无法判断收益来自哪里。

实际复现时还要核对运行参数，因为部分分支在源码中的默认开关仍是开启的。文件名带 `fst` 本身不能证明某次运行只训练了首次转化任务。

### 4. 已经有 DCNM 了，为什么还值得尝试 RankMixer？

我想验证的是另一种组织特征交互的方式。Base 在完整特征向量上做显式交叉；RankMixer 先把字段组织成 Token，再通过固定重排和可学习前馈网络完成交互。这给了我调整分组、Token 宽度、交互深度和信息读出的空间。

但这种方式也有代价。字段进入 Token 时会被压缩，分组不合适或者读出过早汇总，都可能损失有用信息。我的后续实验就不断围绕这些问题展开，例如完整字段切分、语义分组、Global Token、PureFlat，以及压缩前增加显式交叉。

所以研究动机是检验它是否适合当前任务，而不是因为结构更新，就默认应该比已经优化过的 Base 更好。

### 5. 做了这么多版本，最终还是没超过 Base，你的工作价值在哪里？

如果以替换 Base 为目标，我目前还没有完成。Small-3 五日平均 AUC 仍低于 Base 0.0002894，最后一个已有测试日还差 0.000169。这个结果需要直接承认。

已经交付的进展，一是把较宽泛的模型尝试逐步收敛到有具体证据的选择。例如 Small-3 对两层 Small 五日全部提高，对 E2 则在更少 Dense 参数下取得更高的共同窗口平均 AUC。二是留下了能复查的实现、配置和实验记录，包括没有达到预期的尝试，后续可以据此继续验证，而不必重新走一遍。

这些有阶段价值，但还不能替代最终效果。我接下来需要用更集中的实验回答与 Base 的差距，而不是继续用版本数量说明进展。

**追问：你的模型比 Base 还大，这是不是连性价比也输了？**

按当前 Dense 参数量和离线 AUC，这个判断成立。Small-3 约 1.37 亿参数，Base 约 9034 万，前者多约 51.74%，AUC 又更低。因此目前没有证据支持它替换 Base；“参数更少、效果更好”的说法只适用于与 E2 的比较。

### 6. 公司 mature 版本更好，为什么不直接用它？你还继续自己的路线干什么？

如果当前任务是选方案推进业务验证，我不会因为 Small-3 是自己写的就优先选它。mature_v1 在五个共同测试日每天都比 Small-3 高，平均高 0.000334；后续四个热启动测试日平均差距仍有 0.00032375，说明差距不只发生在首日。

mature_v1 还有完整九日结果：前两日略低于 Base，后七日略高于 Base，九日平均差值约为 +0.00004544。这是公司参考结构在当前实验中的结果，应当客观看待。

继续自己的路线需要一个有限、能回答的问题，例如输入加权、Global 信息来源或读出容量究竟怎样影响效果。如果后续既不能缩小差距，也没有成本上的价值，我会建议停止这条分支，把投入转到更有证据支持的方向。

**追问：能不能直接说 mature 的结构设计比你的好？**

可以说当前完整方案的离线结果更好，但不能把差距都归到某一个结构。两者除了 SENet、Token、主干和读出不同，当前保存的学习率衰减下限也分别为 0.5 和 0.1。要解释差距来自哪里，需要先核对实际任务配置，再拆开比较。

## 二、模型设计与代码细节

### 7. 不看代码，讲一遍 Small-3 从输入到预测的完整流程。

输入有 1234 个字段，分为 385 个 common、835 个 item 和 14 个 creative，每个字段的 Embedding 是 17 维，合计 20978 维。

先做分桶 BN 和字段级分层 SENet，再按固定语义组生成 31 个 Local Token，分配是 10、20、1。另用三桶的全量表示生成一个 Global Token，总共得到 32 个 256 维 Token。

然后经过三层独立参数的 RankMixer Block。每层包含固定 Mixing、重排空间的一套 Per-token SwiGLU、Reverting，以及还原布局后的另一套 Per-token SwiGLU。最后做 RMSNorm，把 `32×256` 完整展平为 8192 维，送进 `[2048,2048,256]` 的任务头，通过 Sigmoid 输出首次转化概率。

```text
1234 个字段 × 17 维
  → 分桶 BN + 字段级分层 SENet
  → 31 个 Local Token + 1 个 Global Token
  → [B, 32, 256]
  → 3 层双 FFN RankMixer Block
  → Final RMSNorm → 展平为 8192 维
  → MLP 2048 → 2048 → 256 → 1 → Sigmoid
```

### 8. 为什么要做语义分组？直接均匀切块有什么问题？

早期版本按连续维度切块，大多数块宽度是 1311，不能被单字段的 17 维整除，可能把同一个字段切开，也可能跨越特征桶。它不是在数学上不能训练，但输入组织比较随意。

我先改成按完整字段切分，随后按固定字段 ID 组织语义组，并检查配置顺序与实际 lookup 顺序的映射。这样至少能保证一个 Token 压缩的是明确、稳定的一组信息，而不是输入顺序一变，Token 的含义也跟着变。

v3 与 v2 参数量相同，在 7 月 2 日的直接对照中 AUC 高 0.000301，这是支持分组调整的一条证据。但直接对照只有一天，我不会据此说语义分组已经被证明在所有日期都更好。

**追问：为什么是 10/20/1，这个比例最优吗？**

这个分配结合了字段数量和语义组织，让多数 common、item 组的字段数比较接近，同时给 creative 保留独立入口。它是当前采用的设计，没有完成固定参数预算下的系统搜索，不能称为最优比例。

### 9. Mixing 只是 reshape 和 transpose，没有参数，为什么能产生交互？Revert 不就把它还原了吗？

如果只做置换再做逆置换，确实没有改变。交互发生在两者之间的可学习 FFN。

Small-3 每个 Token 有 256 维，我把它拆成 32 份，每份 8 维，再把所有 Token 对应的一份拼到一起。重排后的一个位置就能同时看到来自 32 个原 Token 的信息，FFN 可以在这些信息之间做联合变换。Revert 只是把坐标放回原布局，不会撤销 FFN 已经完成的变换。

这里固定的是信息路由，可学习的是重排后的变换。它没有按样本计算 Q、K 或注意力权重，代码里的 head 也不能直接当作 Transformer 的注意力头。

### 10. Per-token FFN 和普通共享 FFN 有什么区别？批量矩阵乘是不是把参数共享了？

Per-token FFN 给不同 Token 位置保留独立参数，让不同位置可以采用不同的变换。共享 FFN 则让所有位置使用同一套权重，参数更少，但约束也不同。

批量矩阵乘只是执行方式的整理，权重张量仍保留 Token 这一维，各位置取自己的权重。Local Tokenizer 也是先把输入宽度相同的组放在一起计算，再恢复固定顺序，没有因此共享投影参数。

还有一个容易混淆的细节：重排空间中的位置已经混合了不同原始 Token 的分片，所以不能把其中某套 FFN 继续简单称为“只处理用户画像的 FFN”。

### 11. 一层为什么放两套 FFN？你的残差到底加在哪里？

第一套 FFN 在重排空间处理跨 Token 信息，第二套在还原布局后继续更新表示。两套参数独立，分别对应两种信息组织方式。

代码中的一层可以写成：

```text
m = P(x)
h = m + FFN_m(RMS(m))
r = P⁻¹(h)
输出 = x + FFN_o(RMS(r))
```

最后加回的是这一层最初的输入 `x`，不是 `r`。这样原输入有直接通路，混合后的信息通过第二套 FFN 影响更新。下投影使用小幅随机初始化，目的是控制初始更新的幅度，并不是把新分支完全置零。

我可以说明这些设计在代码中怎么工作，但当前没有逐项拆分“双 FFN、长残差、初始化”的对照，不能给每一项单独分配 AUC 收益。

### 12. 有了 SENet 和 Local Token，为什么还要 Global Token？是不是重复堆模块？

它们承担的工作不同。这里的 SENet 先为字段生成权重；Local Token 把一组字段压成局部表示；Global Token 则从全部字段表示生成一个全局入口，使信息不必只经过各组的局部投影。

Small-3 的 Global 来自三桶 SENet 后的全量输入，所以 creative 同时进入自己的 Local Token 和 Global。这与 mature 将 creative 放在独立支路、Global 取 common/item 的 SENet 前表示不同。

这些路径确实可能存在冗余。我的解释是设计动机，不是已经证明每条路径都不可缺少。要判断 Global 的独立价值，应在相同主干和训练设置下比较有无 Global、不同信息来源，并处理 Token 数或参数量随之变化的问题。

### 13. 你说 PureFlat 更好，会不会只是任务头参数更多？

这个因素在当前实验里确实没有完全分开。v6 的三路读出最终是 1536 维，E2 改成把 `32×512` 展平为 16384 维。虽然任务头隐藏层仍是 `[2048,2048,256]`，第一层全连接却明显变大，总 Dense 参数净增加约 2215 万。

四个共同测试日，E2 相对 v6 平均提高 0.00047925，验证的是完整读出替换后的整套方案。它支持我继续检查读出是否过早压缩，但不能排除任务头容量增加的贡献。

更进一步的实验应该补参数预算接近的对照，例如扩大原读出方案的任务头，观察单纯补容量能追回多少差距，再判断保留 Token 细节的作用。

### 14. 为什么保留 RMSNorm？你的结果能证明 LayerNorm 不适合推荐模型吗？

不能证明这么宽泛的结论。E3 在 E2 上使用当前的 LayerNorm 路径，四个共同测试日都下降，平均差值为 −0.00013675，所以后续 Small 主线保留了 RMSNorm。

RMSNorm 不减均值，LayerNorm 会减均值；但这次替换还包含其他差异。例如部分 RMSNorm 的 scale 是每个 Token 独立的 `[T,D]`，LayerNorm 路径的 gamma、beta 则沿最后一维共享。因此结果针对的是两套具体实现，不能直接归结为是否减均值。

如果继续研究，我会先对齐归一化位置、参数共享方式和训练设置，再比较。现在直接说“LayerNorm 损失了推荐特征信息”，证据还不够。

### 15. Small-3 不就是多加一层吗？为什么认为它比继续加宽更值得做？

它确实是增加一层同构 Block，没有必要把这一步包装得更复杂。前面的 Small 把 E2 的 Token 宽度从 512 降到 256，六日平均 AUC 只下降 0.00004133，Dense 参数却减少了约一半，这让我有理由继续检查容量怎样分配更合适。

Small-3 保持 Small 的输入、RMSNorm、PureFlat 和任务头，只把两层改成三层。五日全部优于 Small，平均提高 0.0001892；与 E2 相比，五日平均提高 0.0001354，参数仍少约 31.24%。

这支持当前这条“缩宽后增深”的实现，但还没有证明相同参数量下加深一定优于加宽。要回答后者，需要补一个参数量接近的两层模型作对照。

**追问：Token 只有 256 维，怎么还有 1.37 亿参数？**

主要因为每个 Token 的 SwiGLU 都有独立参数，每层还有两套。中间宽度保持 704，一套 FFN 是约 1735 万参数，一个 Block 约 3473 万；三层主干合计约 1.042 亿，占总参数约 76%。此外，PureFlat 后的大任务头约有 2151 万参数。“Small”是相对 E2 的命名，并不意味着模型已经很轻。

### 16. Small、Small-1、Small-2、Small-3 是依次升级的吗？

不是简单按编号串行升级，它们有两条不同的末端分支。

Small 保留 RMSNorm、PureFlat 和大任务头。Small-1 从 Small 改成末端 LayerNorm、均值池化和小任务头；Small-2 再在 Small-1 上把两层增加到三层。Small-3 则直接从原始 Small 增加第三层，保留原来的完整读出和大任务头。

因此 Small-3 对 Small 更适合回答“这套结构增加一层会怎样”；Small-3 对 Small-2 则同时涉及末端归一化、读出和任务头。代码设计上的继承也不代表训练时加载前一版本的 Dense 参数，各版本仍按自己的冷启动链训练。

## 三、实验结果与结论可信度

### 17. 不要罗列版本名，讲三项最有依据的 AUC 改进。

第一项是字段分组。v3 与 v2 参数量相同，在 7 月 2 日的直接对照中提高 0.000301。它为重新组织字段提供了单日支持。

第二项是读出。E2 相对 v6，在 8 月 16 日至 19 日四个共同测试日平均提高 0.00047925。这说明完整展平及相应任务头容量的组合值得保留，但不能把容量因素排除掉。

第三项是 Small-3 的增深。它相对两层 Small，在 8 月 16 日至 20 日五天全部提高，平均提高 0.0001892；其中首日提高 0.000049，后续四日平均提高 0.00022425。这一组的直接结构差异更清楚，也是我当前更愿意继续验证的分支。

这三项体现了从输入组织、信息读出到容量分配的改进过程。它们支持的结论强度不同，我不会把单日对照和多日结果说成同样充分。

### 18. v8 的首日 AUC 比 Small-3 更高，为什么你把 Small-3 作为重点？

这个事实需要保留。8 月 16 日，v8 的 AUC 是 0.866615，Small-3 是 0.866559，v8 高 0.000056。因此不能说 Small-3 在所有已有记录中都最好。

我把 Small-3 作为当前重点，是因为它有连续五日结果，也有 Small 和 E2 这些比较清楚的同日参照。v8 目前只有一个测试日，而且同时加入了压缩前 Masked DCN、调整了 FFN 中间宽度，后续效果和具体贡献还不清楚。

如果算力允许，v8 是值得补齐后续日期的候选，而不是已经被淘汰。重点推进 Small-3 是根据已有证据作出的阶段选择，不是证明 v8 没有潜力。

### 19. 哪些尝试没有成功？你从中得到了什么，而不只是“继续调参”？

例如 v4 增加定向 Query–Item 交互，7 月 2 日反而比 v3 低 0.000282。这提醒我，业务上容易解释的交互，不一定在现有主干上提供额外有效信息。

再比如 v8 在首日比 v6 好，但继续加入更多 DCNM、双视图和 Shortcut 的 v9，首日效果又下降了。E3 的归一化替换也在四个共同日期都没有改善。它们共同说明，多加模块或者换成看起来更合理的结构，都需要重新验证。

这些结果帮助我暂时收敛到已有多日支持的分支，但还不能证明“DCN 不适合 RankMixer”或“LayerNorm 不适合 CVR”。不少版本同时改了几个位置，需要保留失败记录和配置，避免把一次组合失败误判成某种机制无效。

### 20. 不同版本训练天数不一样，你怎么比较？你说的 52 条实验又是什么意思？

我先找共同测试日，逐日计算两个模型的 AUC 差值，再对这些差值取平均。例如 E2 和 Small 各有六日结果，可以比较六日；Small-3 只有五日，与它比较就只取共同五日。mature 的完整九日结果可以与同日 Base 比，但不能直接拿九日均值减 Small-3 的五日均值。

52 条指个人主线中有源码的 17 个模型，按“模型—测试日期”去重后的结果记录。它们包含同一个模型的逐日续训，不是 52 次独立随机试验。18 个主要实现中，v10 还没有独立 AUC 记录，也不能补算成已验证成功的模型。

**追问：模型自己的 AUC 从第一天涨到第五天，能证明热启动有效吗？**

不能只凭这个判断，因为测试数据每天在变。观察连续训练表现应看同日对照；如果专门研究热启动本身的作用，还要设计在同一测试集上比较不同训练历史的实验。另外，按日等权平均的 AUC，也不等于合并所有样本后计算一次总体 AUC。

### 21. 既然是冷启动，为什么 Sparse 又热启动？这样公平吗？

这里的冷启动专指 Dense 部分。首日不继承旧 Dense checkpoint，各参数按本模型的初始化方式建立；Sparse Embedding 则继承已有参数。这样能在已有稀疏表示基础上研究 Dense 结构，也避免把稀疏表完全从零学习的影响混进来。

Base 和候选方案采用相同的首日启动协议，后续各自只加载同一版本前一天的参数。7 月和 8 月是两条独立训练链，8 月并不接着 7 月的 Dense 训练。

这种设置下比较的是“共同 Sparse 起点下，各方案经过训练后的效果”。Sparse 热启动不等于冻结，后续它仍会更新；不同 Dense 主干也可能通过梯度影响 Sparse 的学习。因此结论不应扩大为完全随机初始化下的优劣，也不是把训练后的 Sparse 严格固定后的纯 Dense 表达能力比较。

### 22. 你怎么确认 Dense 真的冷启动了？训练条件真的全部一致吗？

我会同时核对首日运行参数、checkpoint 恢复日志和模型输出目录。参数上要忽略 Dense 恢复、保留 Sparse 恢复；目录也应是独立的新目录，否则自动加载已有 checkpoint 的逻辑可能让预期的冷启动变成续训。后续则检查只加载本版本前一天的模型。

比较时还要核对样本范围、特征版本、训练步数、batch、优化器和学习率曲线，不能只看基础学习率写得一样。当前保存的 Small-3 与 mature 的 `min_rate` 不同，说明“相同数据和启动方式”不等于“全部训练超参数完全一致”。

当前本地还保留了一些旧日期模板，不能据此还原所有历史任务的最终设置。要完整复现，应保存当次任务展开后的配置和恢复日志，而不只留一份可能继续被修改的 args 文件。

**追问：代码里的 `warmup_steps=60000` 是前六万步线性升学习率吗？**

在这里采用的 `gauss_decay` 路径中，它表示衰减前的平台阶段，之后再进行高斯衰减，不能凭参数名解释成线性 warmup。学习率还受 checkpoint 恢复和 milestone 处理影响，所以应核对实际曲线。

### 23. 只提高万分之一到万分之二，怎么知道不是噪声？五天都好就显著了吗？

现有结果不能让我下统计显著的结论。Small-3 对 Small 的五个同日差值都为正，是方向一致的观测；但五天属于同一条连续训练链，不是五个独立随机种子的重复实验。

进一步判断需要保留同一批样本上的模型预测，按请求或用户的相关性设计配对不确定性分析，再补独立初始化的重复训练。前者帮助判断测试样本波动，后者帮助了解训练随机性，不能互相替代。仓库已经有按请求分组的配对分析工具，但当前汇总没有相应置信区间结果。

还要处理模型选择偏差：尝试过很多版本，又反复查看同一批日期，最终挑出的最好结果可能包含偶然因素。因此我会冻结候选结构，用尚未用于选型的新日期确认，再决定是否扩大验证。

**追问：你已经记录到小数点后六位，还需要担心评估误差吗？**

需要。显示六位小数不等于误差小于百万分之一。当前代码有 2000 阈值的 AUC 计算路径，应确认最终汇总来自哪条累计评估链路，并用同样本预测复核差值对计算精度是否敏感。样本很多，也不能直接代替这些检查。

### 24. 你要提升 AUC，为什么训练用二分类 log loss，而不直接优化 AUC？

当前任务既需要排序，也要输出转化概率，代码沿用二分类 log loss 训练，AUC 作为核心评估指标。log loss 对每个样本给出连续的优化信号，与当前训练框架的概率预测任务相匹配。

AUC 主要看正例是否排在负例前面，和概率数值是否准确不是同一件事。因此 loss 下降不保证 AUC 一定提高，AUC 提高也不保证校准更好。

我这阶段的改动集中在模型结构，没有完成直接优化排序目标的对照。如果后续尝试其他损失，需要同时检查排序、概率尺度和实际训练成本，不能只因为评价指标叫 AUC，就认为直接换损失一定更合适。

### 25. Small-3 的 AUC 提高了，COPC 却更差，这到底算不算改进？

它是当前窗口里的排序指标改善，不是所有指标一起改善。代码中 COPC 是总预测量除以总正例量，大于 1 表示总体高估，小于 1 表示总体低估。

Small-3 五日 COPC 在 0.981053 到 1.017099 之间。按日期平均的 `|COPC−1|`，Small-3 是 0.0120376，Small 是 0.0105582，E2 是 0.0042476，因此不能说 Small-3 的校准也更好。这种平均偏差是描述性汇总，也不等于合并五日样本的 COPC。

后续我会检查偏差来自哪些日期、预测分段和业务人群，再决定是否需要校准或训练调整。即使整体 COPC 等于 1，不同群体的高估和低估也可能互相抵消，仍需分层看。

**追问：把所有预测乘一个系数，让 COPC 接近 1，不就解决了吗？**

它可能修正整体尺度，却不能保证局部概率准确。严格单调变换通常不改变排序，但最终概率还要落在有效范围内；如果截断产生并列分数，排序指标也可能变化。任何校准参数都应在独立验证数据上确定，不能用测试标签调完后，再把同一测试集的改善当作新结果。

### 26. 搜索是在一次请求里排序，你只看全局 AUC，是否看错了指标？

全局 AUC 是这组实验的统一主指标，适合延续已有对照，但它包含跨请求的正负样本比较，不能完整回答一次搜索请求里的候选是否排得更好。

因此我会补按请求的分组评估，并明确哪些组能够计算、怎样加权，以及只含单一标签的请求怎样处理。还应看关键业务分层，避免整体改善主要来自某类流量占比或跨请求分数差异。

当前配置有 GAUC 开关，但最新汇总表没有对应数值，所以我不能声称已经验证了请求内排序提升。配置支持某项指标，与已经有可引用的结果，是两件事。

## 四、工程实现、复现与问题排查

### 27. 参数少了 31.24%，能说训练或推理也快了 31.24% 吗？

不能。这个比例是 Small-3 相对 E2 的 Dense 可训练参数差异，不包括稀疏表、优化器状态和激活内存，也不能直接换算成耗时。

实际速度还取决于矩阵形状、算子数量、硬件利用率、数据读取和分布式通信。模型更深还会改变执行依赖，即使参数减少，时延也不一定同比例下降。

最新表中 E2 登记了 560 分钟、v6 登记了 440 分钟的训练耗时，但没有 Small-3 的对应实测记录。这些也不是线上推理延迟。后续需要在相同资源条件下测吞吐、内存和实际服务批量下的延迟，再谈成本收益。

### 28. 除了改模型结构，你做过什么具体的工程优化？

一个方向是把独立 Token 的投影和 FFN 整理成批量矩阵乘，同时保留各自参数；另一个是把同宽 Token 投影后的多次切片改成一次 Unpack，再恢复固定顺序。

原来的多次切片在反向图中可能分别构造回填到完整尺寸的梯度张量，再累加。Unpack 可以整理这条路径，减少重复的图结构和中间张量。这类修改的目标是改善执行方式，不改变模型表达。

我也保留参考路径和优化开关，便于单独验证。当前不能据理论中间张量体积的减少，就宣称实测峰值显存或训练时间下降了某个比例。

### 29. 你怎么证明工程优化没有改变训练？前向一样就够了吗？

不够。前向一致不代表梯度、优化器状态和恢复后行为都一致。

仓库的验证工具对照参考与优化 Tokenizer，检查输出、探针损失、输入梯度和参数梯度，还用原生 Adam 检查三步更新、优化器状态以及 checkpoint 恢复，并覆盖不同 batch 和分区配置。

但这仍是独立 Tokenizer 的验证，不等于完整 CVR 训练图已经等价。它没有替代 FloodAdam、Flood BN、PS 和生产数据路径的验证。当前资料也不足以说这些检查已经在生产环境完整通过；要支持这样的结论，需要相应环境的运行结果。

### 30. 代码和测试都可靠吗？别人接手能不能复现？

已经有一些必要的保障，例如字段覆盖、重复和顺序检查，Token 维度与参数量检查，以及各版本保存的独立入口和参数文件。这些能减少“形状相同、语义却错位”和复制版本时的意外修改。

但当前还存在维护欠账。最新复核记录中，Small 系列 32 项测试有 28 项通过、3 项因缺少 TensorFlow 环境跳过、1 项未通过。未通过项仍要求 Small-3 与原 Small 的外层日期和 checkpoint 参数一致，与现有文件不符；结构和三层参数相关检查通过，但不能据此写“全部测试通过”。

要让接手者真正复现，我会把代码版本、最终展开配置、特征版本、数据日期、checkpoint 来源和结果位置一起固化，区分结构测试与运行配置检查，并在目标环境补齐数值和建图验证。多份文件已经保存下来，是起点，还不是完整复现证据。

### 31. 你预测的“首次转化”到底是什么？是用户人生首单吗？有没有标签泄漏？

本次建模沿用团队提供的 `fst_cvr_label`。当前代码能确认的是，它从上游样本中读取这个标签，作为唯一主任务，用二分类 log loss 训练，输出入口叫 `first_cvr`。仅凭字段名，不能把它自行解释成用户人生首单。

关于“首次”针对的对象、转化归因窗口和延迟回传规则，需要回到上游样本生成口径确认。我的工作主要在模型侧，现有模型文件本身不能完整证明这些业务定义。正式答辩前，这也是我必须补齐的业务说明。

检查泄漏时，我会核对特征在预测时是否已经可用、统计特征的截止时间、训练测试分区、Sparse checkpoint 时间，以及标签回填是否跨越了约定窗口。按日期训练、次日测试是必要的时间划分，但单凭这一点还不能证明完全没有泄漏。

### 32. 假如新版本 AUC 突然下降，你会按什么顺序排查？

我会先判断是不是一个有效可比的结果：测试日期和样本范围是否一致，是否有文件缺失、异常退出、预测丢失，评估是否使用同一条汇总链路。代码存在异常后提前结束测试的路径，所以看到一个最终数值，还要确认样本是否完整。

接着检查训练状态：是否加载了正确的 checkpoint、Dense 是否按预期初始化、学习率是否符合设定，以及 loss、预测均值、正例数和 COPC 有没有异常。小差值还要核对同样本评估和数值计算口径。

这些都正常，再看结构改动，回到最接近的父版本做对照。若只看到总 AUC 下降，就立即再加一个模块，很容易把输入或配置问题掩盖过去。排查后的结论也要区分“已定位原因”和“还需要验证的假设”。

## 五、复盘、后续安排与转正判断

### 33. 你是在系统研究，还是没有方向地试参数？如果重做一次，会怎么改？

前期有些版本确实同时改了多个模块，能够判断完整方案有没有改善，却不容易回答哪一项起了作用。这是我会主动复盘的地方，不能用版本多替代实验质量。

后期开始围绕 v6 拆问题：E2 看读出接口，E3 看当前归一化实现，Small 看宽度，Small-3 在 Small 上增加深度。不过即使只增加一层，也同时增加了参数，仍要说明对照能够回答到什么程度。

如果重做，我会更早固定比较日期和记录格式，把探索实验与确认实验分开。探索阶段可以联合改动来找方向；一旦出现改善，就补关键对照和新日期验证。算力有限时，优先做能影响下一步选择的实验，而不是把所有想到的模块都实现一遍。

### 34. 再给你两周，你会具体做什么？别说“继续优化模型”。

我会先补证据，再决定改哪里。

第一步，整理 Base、Small、Small-3 和 mature 对照的实际训练配置，补齐 Small-3 后续热启动测试，并保存同样本预测和运行成本。这样先回答五日改善能否延续，以及与参考方案的差距是否一直存在。

第二步，只选一个最关键的结构问题做对照。例如保留 Small-3 的其他设置，用参数量接近的两层模型比较，检查当前收益是否更值得分配给深度；或者针对 PureFlat 做预算接近的读出对照。两者不会一口气混到同一个版本里。

第三步，冻结候选，在新日期上确认 AUC、COPC 和关键分层表现，输出继续、调整方向或停止的结论。具体能跑多少任务取决于资源和单次耗时，我会先排优先级，不承诺两周内一定超过 Base。

### 35. 什么时候应该停止？如果离线超过了 Base，就可以上线了吗？

是否继续应看效果、成本和剩余问题的价值。若补齐验证后仍低于 Base，资源开销也更高，而且新的实验不能提出有依据的改善方向，我会建议停止当前分支，转向更有潜力的方案。继续训练多少天、能接受多大差距，应在实验前结合业务目标和算力预算确定，不能每次结果不好就临时延长。

即使离线超过 Base，也只是下一阶段的入口。还要确认新日期、请求内排序、校准和关键分层没有明显问题，完成服务兼容、延迟和稳定性验证，再按团队流程做可回滚的线上实验。

线上需要看实际转化、成交相关指标以及延迟等约束。离线 AUC 差值不能换算成线上 CVR 增长，当前也没有属于我这套方案的线上 A/B 收益可以引用。以上是后续验证路径，不是已经完成的上线成果。

### 36. 如果评委最后问“为什么应该给你转正”，你怎么回答？

这段实习中，我已经能围绕一个具体模型问题，把已有方案整理成可比较的基线，完成代码改动和训练配置，再根据结果决定下一步。面对早期效果不理想，我没有只停留在调整参数，而是逐步检查输入组织、交互路径、读出和容量分配，并留下了对应的实现和结果。

我也更清楚自己目前的不足：前期组合改动多，部分实验窗口偏短，复现记录和统计证据还需要补齐。最新方案没有超过 Base，我不会把相对旧版本的改善说成已经取得业务收益。

如果继续留在团队，我希望承担从问题分析、实验设计到结果复盘的完整任务，把实验做得更有针对性，也更重视成本和交付。对我来说，后续需要证明的是能否持续给团队提供可靠的判断，并把有价值的方向推进到实际效果。

## 练习时怎样使用

时间有限时，先练第 **1、2、5、6、7、13、17、21、23、34** 题。它们覆盖项目主线、贡献归属、当前差距、核心设计和后续安排。第 9、11、15 题适合配合白板，检查自己是否能讲清张量变化、残差和参数来源。

遇到尖锐追问时，先回答对方指出的问题是否成立，再给数据或代码依据。例如“任务头确实变大了”“当前还没有超过 Base”，随后解释这个实验实际验证了什么。承认限制后仍然要给出自己的判断和下一步，不要只重复“还需要更多实验”。

正式答辩前，应补齐第 31 题的上游标签定义，并核对能取得的历史任务最终配置、生产验证和线上状态。若取得了新结果，再更新对应回答，不沿用这里的阶段结论。
