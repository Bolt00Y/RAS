## 3. Scale up 的轴必须从实际权重形状解释

### 3.1 T、D、L、M 不构成同一种增长关系

普通逐 Token 两投影 FFN（中间宽度 kD）主项为：

`P ≈ 2kLTD²`，`Forward FLOPs ≈ 4kLTD²`。

v5/v6 两个 SwiGLU 的 Block 计数为：

`P_swiglu = T(3DM + 2M + D)`；

`P_block = 2P_swiglu + 2TD = 6TDM + 4TM + 4TD`。

这里 Block 的两个 RMSNorm 各有 T×D scale。无参 Mixing/Reverting 不增加参数，但产生张量布局变换的内存开销。真实代码中 `w_up/w_gate/w_down` 均有 Token 维，两个 stage scope 和每层 block scope 均独立，见 [Small-3 权重及 Block](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_bn_rankmixer_v6_e2_small_3.py:1780)。

因此不能笼统说“D 翻倍参数翻四倍”：**现有 v5→v6、E2→Small 固定 M=704，Block 主项对 D 近似线性**；有效 `M/D` 分别为 0.6875、1.375、2.75。只有另行固定 `M=rD` 时，Block 参数才对 D 呈二次增长。现有“扩宽”还同步改变输入投影和 Flat→首层任务头；这可作为整个网络的宽度扩展，但不能归因为只加大 FFN。

mature-v1 则固定 expansion=3.5，即 M=3.5D；每 Block 一次 SwiGLU，约 `3TDM`。mature-v4/v5 使用两投影 pSiLU，主项改为 `2TDM`。所以 **Small-3 和 mature-v1 同为 L3，不代表相同 FFN 深度；mature-v1→v4 也不是纯 D256→D384。** [mature-v1 配置](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_senet_mature_rankmixer_v1.py:269)、[mature-v5 pSiLU](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_senet_mature_rankmixer_v5.py:1698)。

### 3.2 批量 MatMul 不等于共享 FFN

v1 的实现按 `rm_pffn_t{t}` 建独立变量；v5/v6/mature/UniMixer 将变量打包为 `[T,D,M]` 做批量 MatMul 或 einsum，参数仍按 Token 独立。将它误认成共享 FFN 会少算近 T 倍的主干权重。[v1 独立 scope](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_bn_rankmixer_v1.py:815)、[UniMixer 权重](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_bn_unimixer_v1.py:455)。

若未来把 FFN 权重在 Token 间共享，主导参数可从 `T×3DM` 减到 `3DM`，但所有 T 个 Token 仍执行 FFN，样本 FLOPs 基本不变。**等参数与等计算是不同对照条件**。本次没有找到可对应结果的 shared-FFN 消融，故不能声称已验证 Token 专属权重的独立收益。

这些架构的 Dense 前向为固定稠密路径，没有 top-k MoE 条件激活；“active Dense 参数”在结构意义上接近所列连接到任务输出的稠密权重。但实际某步梯度非零数、参数利用率、稀疏 active key、权重 effective rank 均未测量，不能拿总参数替代这些统计。

### 3.3 Token 数与输入投影存在另一种容量规律

对每个字段仅进入一个 Token、每 Token 输出 D 的分组，Local kernel 总数是 `ED`；改变组边界本身不改变总数。v2/v3 属此类，v6 语义均衡与固定组大小随机化也可保持相同参数。

mature-v1/v4 的输入做法不同：某业务粗组有 n 个字段，**同一组联合投影成 k 个 Token**，kernel 数为 `17n×kD`。mature-v5 让每个字段只进入一个语义 Token，kernel 变成 `17n×D` 的逐组求和。因此它的 Local 容量从 **37.193088M 降到 7.999872M**，总计减少 **29.193216M（17.6963%）**，FFN、主干深度、D、读出和旁路不变。若其 AUC 同时改善，证据应解读为“更细的输入组织在减少容量后仍有优势”，不能解读为总参数 scaling law；也不能单独排除降参带来的泛化作用。[mature-v5 精确计数](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_senet_mature_rankmixer_v5.py:867)。

## 5. 旧材料和配置漂移的修正

1. **mature-v5 199M 备注不应进入参数效率图。** 当前源码静态计数为135,774,879，与旧版结果表135.775M及独立介绍一致。0909 报告结果表中的199M和当前代码不一致，应保留为资料冲突。历史任务若确实用另一份199M实现，应拿回对应源码/图 manifest 后另建版本，不将当前135.775M强行绑定那次任务。
2. **Small-2/Small-3 都是三层。** 名称序号不是层数，Small-2来自Small-1，Small-3来自原Small；不能排成 L2/L3/L4 的三点深度曲线。
3. **“纯读出”替换可能增加参数。** v6→E2删掉若干读出子模块，却使任务头首层输入由1536变成16384，Dense从177.217126M增至199.367013M。算总参时不能只减去被删除的模块。
4. **v1_lrfix 是训练逻辑修复。** 它增加训练初始化时 milestone reset，而前向参数不变。原v1旧任务的学习率是否正确不能仅凭新的lrfix代码确认。[lrfix reset](/Users/goku/Documents/Codex/RSA_code_0816/src/models/rankmixer/cvr_bn_rankmixer_v1_lrfix.py:697)。`enable_dense_warmup=false` 指 checkpoint/支路 warmup 的开关，不等于 gauss LR schedule 的60000步 warmup关闭；Small-3和mature的schedule仍默认启用。
5. **当前 args 不等于历史训练协议。** 本次只读并保留用户的 E3/v10 修改：目前二者源码 args 的训练日期为08-15、测试08-16、Sparse checkpoint来源08-14；E3历史材料保留过08-14训练/08-15测试。这不改变本表固定P/F，但足以改变结果可比性。两个文件的SHA与当前日期已写入CSV，没有回写或“修复”用户参数。
6. **动态 U 相同是条件假设，不是代码结论。** 旧参数材料中“相同日期/起点/策略下U相同”只可作为预算前提；若 lookup更新、过滤、生命周期、训练中断或输入样本不同，实际Sparse表应由checkpoint manifest核对。

## 8. 计算量与时间的结论边界

所有FLOPs采用1 MAC=2 FLOPs；激活、Norm为统一标量算术近似，transpose/concat按0算术FLOPs处理。这个口径有比较价值，但不能推出吞吐、延迟、显存或价格。Small的Token构造unstack优化不改参数/矩阵算术，却可能减少反向StridedSliceGrad中间张量；这是计算图布局优化的证据，恰好说明参数/FLOPs和实际成本并不一一对应。

粗略训练成本常以 `每步样本数×前向FLOPs×反向系数` 预算，但本项目有PS、稀疏lookup、BN、Adam和异步/数据输入成本，不能把反向系数固定为3再称为已测训练compute。应保存至少：有效训练样本/正例、优化步数、worker数、每worker batch、step time、examples/s、内存峰值、真实训练时长、导出推理p95/p99；“535分钟”和“135.8M参数”分别是运行结果与静态预算，必须有同一次任务的证据后才组成效率点。
