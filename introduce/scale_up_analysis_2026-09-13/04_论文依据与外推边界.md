# 论文依据与外推边界：现有结果能支持怎样的 scale up 判断

> 日期：2026-09-13。本文核对仓库内 5 篇原始 PDF、已有论文详解，以及 v6-E2-Small 系列的运行参数和主干实现。页码均指本地 PDF 的物理页码。文献中的数值只表示论文自己的实验，不计入本项目实证；本项目的结果清单、参数和配对比较以本目录其他报告为准。

## 1. 可以形成的判断

文献支持继续研究 scale up，但没有提供“直接增大 D、层数或参数就必然提升本项目 CVR”的保证。更具体的工作假设是：**先确认当前结构能将新增计算转化为任务有效信息，再共同扩展模型和训练预算；扩张方向、输入组织、读出方式及训练稳定性需要一并检查。**

这也是理解本仓库已有现象的合适方式：小模型表现更好时，可能说明原配置容量分配、优化或数据预算不匹配；它不自动证明所有大模型都无效。加深产生改善时，说明特定结构在已测深度范围内存在可利用空间；它不自动证明任意加深都满足同一规律。

本文将证据分为三类：

| 类别 | 能回答的问题 | 不能替代什么 |
|---|---|---|
| 论文实测 | 其他任务、数据和系统中，哪些扩张策略曾奏效 | 本项目增益大小、训练时长、线上成本 |
| 本项目代码与结果 | 当前具体实现和历史配置在已测样本上的表现 | 未运行配置的表现、缺失日志中的训练过程 |
| 本文提出的待验证假设 | 下一步如何排除混杂、定位瓶颈 | 已成立的因果结论或 scaling law |

最重要的表述边界是：**结构适配结论、有限范围的规模趋势、可预测的 scaling law，是逐级增强的三种结论。** 当前材料若只覆盖少量规模点且配置联动，只宜使用前两种；不能把跨方案散点拟合成普适幂律。

## 2. 五篇论文分别提供什么证据

### 2.1 RankMixer：参数能否扩大，取决于架构与硬件是否共同改善

原论文 Table 1、Figure 2 展示了约 100M 到 1B 稠密参数的性能与计算扩展。这里的参数不含稀疏 embedding 表，训练 FLOPs/Batch 使用 batch=512。§4.3 指出，在作者所测范围内，扩展 D、T、L 的效果较接近；加宽形成更大的矩阵乘，MFU 较高，因此部署配置保持两层并增加宽度与 token 数。这是具体系统中的经验，不是 D、T、L 在任何模型上的等价定理。[RankMixer v3，PDF p5-p6](https://arxiv.org/pdf/2507.15551v3)

Table 6 的服务对照更有解释价值：15.8M→1.1B 参数伴随 107G→2106G FLOPs，MFU 从 4.47%→44.57%，计算精度从 fp32→fp16，延迟为 14.5ms→14.3ms。**近似不增延迟是参数利用、算子组织与精度变化的联合结果。** 它不能用来承诺本项目把参数扩大约 70 倍也能维持延迟；本地普通 batched matmul 也不等价于论文部署系统的融合内核。[RankMixer v3，PDF p7，Table 6](https://arxiv.org/pdf/2507.15551v3)

对本项目的可执行启示：参数数目只能作为容量轴；还要记录训练/推理 FLOPs、真实吞吐、延迟和硬件利用率。若模型更小但读写更多、串行层更长，实际成本未必更低。

### 2.2 TokenMixer-Large：小规模时的扩张经验不能直接外推到大规模

这篇后续论文明确修正了原先的经验。§4.4.2 说，在超过约 1B 的实验中，仅扩大宽度、深度或 SwiGLU 中间扩张倍数都会逐渐遇到瓶颈，均衡扩大多个维度更有效；同时更大模型需要更多训练数据才能充分收敛。它还引入 Mixing/Reverting、残差、Pre-RMSNorm、跨层连接和辅助监督，以改善深层优化。[TokenMixer-Large v2，PDF p3-p4、p7](https://arxiv.org/pdf/2602.06563v2)

Table 4 对直播任务展示不同规模和训练天数下的 ΔUAUC，2.3B 的 30d/60d 两行分别记为 +0.41%/+0.70%。**表下注释对逐行基线的文字与最后一行的规模不变存在解释空间，因此这里不把两行相减当作严格的单因素数据增益。** 可以稳妥引用的结论是作者报告延长数据训练有助大模型收敛，不能照搬“本项目必须训练 60 天”的阈值。[TokenMixer-Large v2，PDF p7，Table 4](https://arxiv.org/pdf/2602.06563v2)

稀疏扩张也必须分口径。Table 2 中，4.6B dense 与激活 2.3B / 总量 4.6B 的 Sparse-Pertoken MoE 报告相同 ΔAUC，训练 FLOPs/Batch 从 29.8T 降至 15.1T，batch=2048。附录 A.1 选择 1:2 稀疏方案用于上线；更高稀疏率的效果与负载均衡尚有代价。这个结果支持“先验证大 dense 模型收益，再研究稀疏降本”，不支持直接增加专家总数即可扩大有效学习能力。[TokenMixer-Large v2，PDF p6、p10](https://arxiv.org/pdf/2602.06563v2)

另一个值得保留的假设来自附录 A.3：前置 DCN 的报告收益随主干规模增大而减弱。因此本项目可以测量“显式交叉收益是否依赖主干规模”，但不能因论文在 700M 附近出现冗余，就提前删去本项目 Base 里的有效结构。[TokenMixer-Large v2，PDF p10-p11，Table 9](https://arxiv.org/pdf/2602.06563v2)

### 2.3 RankUp：扩张可以从输入信息与任务分工入手

RankUp 的主要变化在表示形成与任务读出：固定随机置换分片、多 embedding、Global Token、预训练 embedding 交叉和 Task Token。论文 Table 1 分别报告组件消融；Figures 3-4 检查 token 多样性和逐层表示谱。部署是约 10M→100M、两层主干、32 个任务、18 个月训练数据。这类证据更适合支持“扩大可用表示空间”的设计方向，而不是把所有收益归因于主干变大或层数变深。[RankUp v3，PDF p2-p7](https://arxiv.org/pdf/2604.17878v3)

随机分片与语义分组看似冲突，其实控制变量不同。RankUp 观察到某些语义组聚集长尾字段、冗余较高，随机分配会分散这些因素。本项目此前的“语义分组优于连续字段切分”也不等于“语义分组优于所有随机策略”。合理的新对照应保持字段完整、token 数、每组输入维度、桶结构和训练预算一致，只改变字段成员，并固定多个分组随机种子。

注意三个边界：

- Multi-embedding 会扩大稀疏参数与访问成本；外部预训练向量会引入新增信息，均不能记成纯 dense scaling。
- Task Token 的动机依赖多任务冲突；本项目若只评估单一 first CVR 目标，其适用条件不同。
- Global Token 可帮助信息接入，但最终 rank 较高并不证明新增信息与转化标签有关，仍要同时验证预测指标。

### 2.4 RankElastor：有效秩是有用诊断，但现有论文不足以给出本项目阈值

该论文使用 Full Mixing 与带门控/可学习残差的 FFN，希望改善“mixing 扩谱、FFN 缩谱”的动态。主实验对照 RankMixer，Criteo/Avazu 的 AUC 绝对提升分别为 0.00107/0.00053；主表是 10 次初始化均值，未给各次结果或误差条。Figures 7-8 展示扩宽、扩深及联合扩张的局部趋势，但不足以预测本项目的最优规模。[RankElastor v1，PDF p6-p9](https://arxiv.org/pdf/2605.23191v1)

本次回看完整页面确认了一处实质口径问题：p2 式(1)使用 stable rank；p6 设置 (T,D)=(15,26)/(16,24)；p8 的图注称逐样本/逐层有效秩，图中却存在约 22 的数值。若确实对这些 T×D 矩阵逐样本计算，stable rank 与熵型 rank 都不能超过 min(T,D)=15/16。**原文未在这些页面说明另一个计算矩阵或形状，故绝对值不可作为本项目健康阈值。** 这不推翻其所有 AUC 结果，但削弱了从图中精确秩数值推导机制的证据强度。

Full Mixing 的成本也不宜轻描淡写。其权重矩阵是 (TD)×(TD)，单层参数为 (TD)²。套入本项目常见 T=32：

| D | TD | 单个 Full Mixing 的权重数 | 仅 FP32 权重存储 |
|---:|---:|---:|---:|
| 256 | 8,192 | 67,108,864 | 256 MiB |
| 512 | 16,384 | 268,435,456 | 1 GiB |

这是由维度直接计算的工程估算，未包含梯度、优化器状态、激活和其他模块，训练驻留开销会更高。因而若需要可学习 mixing，应先试结构化/分组方案，再决定是否值得全矩阵展开。论文所报约 10%-15% 训练耗时增量来自它的小 T×D 设置，不能转用于本项目。

### 2.5 UniMixer：最优扩张方向与 mixing 结构有关，省参数不等于省 FLOPs

Table 4 给出了有辨识力的深度对照：RankMixer 2→4 blocks 的 AUC 为 0.747772→0.746706；UniMixer-Lite 2→4→8 blocks 为 0.749228→0.750803→0.750875。其意义是结构改变后深度收益可以恢复，同时 4→8 的边际收益已明显减小。这个外部任务上的局部对照不能决定本项目应采用几层。[UniMixer v2，PDF p13，Table 4](https://arxiv.org/pdf/2604.00590v2)

Table 2 也说明“参数效率”和“计算效率”需分别读：例如 67.5M 的 UniMixer 为 2.07T FLOPs/Batch，而 135.5M 的 RankMixer 为 1.68T；另一个 38.2M 的四层 Lite 为 1.26T。不同配置处在不同的参数/计算折中位置，不能只根据 Lite 名称或最小参数宣称成本最低。[UniMixer v2，PDF p10，Table 2](https://arxiv.org/pdf/2604.00590v2)

论文 p11 给出特定留存任务上 ΔAUC 与参数/FLOPs 的幂律拟合。这里不复制指数作为本项目先验：基线偏移、指标口径、容量区间、训练协议和拟合数据都不同；AUC 有上界，增益幂律更不能无限外推。参数压缩矩阵的分解秩，与激活矩阵的有效秩，也不是同一个量。

## 3. 如何把“有效秩”变成可靠的本项目测量

截至本次检索，在 `src/`、`scripts/` 和 `introduce/` 的 Python 文件中未发现 `erank/effective_rank/stable_rank/tf.svd/linalg.svd` 等直接实现。该搜索不覆盖平台侧私有代码，因此只能说明本地材料尚不能支撑“已经观测到本模型表示坍缩”。应先补测，再解释。

### 3.1 同时测两种谱指标，并固定轴

令 X 的非负奇异值为 σᵢ，且 X 非零：

\[
 r_{stable}(X)=\frac{\sum_i\sigma_i^2}{\sigma_1^2},\qquad
 r_{entropy}(X)=\exp\left(-\sum_i p_i\log p_i\right),\quad p_i=\frac{\sigma_i}{\sum_j\sigma_j}.
\]

RankElastor 正文采用前者，RankUp 采用后者。二者都在 [1,min(行数,列数)] 内，但对小奇异值的敏感性不同，数值不能直接比较。零矩阵应单独记零/退化标记；epsilon 只作数值保护，不能把全零分布误算为健康秩。

对 H∈R^(B×T×D)，至少区分：

| 测量矩阵 | 目的 | 理论上限 | 注意事项 |
|---|---|---|---|
| H[b,:,:]，逐样本 T×D | 一个样本内的 token 表示多样性 | min(T,D) | 每个样本先算，再报告均值、分位数 |
| H[:,t,:]，逐 token B×D | 某个 token 跨样本的表示变化 | min(B,D) | 解释长尾语义组，保持采样 B 一致 |
| reshape(H,[BT,D]) | 总体通道空间分布 | min(BT,D) | 混合了样本与 token，不能冒称逐样本秩 |
| reshape(H,[B,TD]) | 整个样本表征的多样性 | min(B,TD) | 易受批次规模与样本分布影响 |

同时保存原始指标与除以上限后的利用率。特别是 **T=32 且 D≥32 时，逐样本 T×D 的秩上限一直是 32**；加宽 D 不提高这个上限。因此“D 加倍但逐样本 rank 没加倍”并不是加宽失败的充分条件。需要结合跨样本通道谱、标签可预测性和主任务指标。

中心化也必须固定。LayerNorm 会去除逐 token 均值，RMSNorm 不会；若只比较未中心化谱，可能把均值方向的改变当成表示改善。建议同时记录原始矩阵和沿被测样本/行轴中心化后的谱，并在图名中写明轴、是否中心化及是否包含残差。

### 3.2 哪些层值得采样

按实际图结构采样 tokenizer 输出、mix 后、mixed FFN 后、revert 后、original FFN 后、block 输出、final norm 后和读出向量。v6 系列每个 block 有两个独立 SwiGLU，不能用“一个 FFN 后”混过两个阶段。

对不同 D、L 使用相同验证样本 ID、相同标签成熟窗与相同批次采样；分训练进度记录。优先在固定验证样本上离线测谱，避免全量训练阶段频繁 SVD 影响吞吐。诊断集合中长尾字段/低活用户等分层规则应训练前固定，防止事后只挑有利子集。

同时记录训练/验证 LogLoss、AUC、梯度范数、每层更新量与残差范数比、是否出现 NaN，以及读出前后的可预测性。谱升高可能只是引入无关变化；只有在公平训练下同时改善预测、校准或泛化，才支持“更多有效容量”的解释。

## 4. 文献导出的可选完整实验设计

以下是由文献机制推导的可选完整设计，尚未运行，不代表另一套首批排期。**本项目的执行顺序、优先配置和代码准备要求以 [05_后续验证方案.md](05_后续验证方案.md) 为准：先比较 Small 两层/三层、D352 两层、M1056 两层及同日 Base，再考虑 L4。** 本节保留较完整的变量网格，供资源充足时扩展。配置数字来自当前 Small 系列的 T=H=32、D=256、M=704、L=2/3；其中 M 表示 SwiGLU 中间绝对宽度。现有代码含固定架构/参数断言，新点需要先准备统一可配置实现并建图验证，不能仅改 args 提交。每个新实验需保存独立参数文件、代码 hash、数据窗与最终生效配置。

### 4.1 可选规模网格：固定结构，识别扩深与扩宽的局部斜率

建议以同一 Small + PureFlat 结构为锚点，固定语义分组、Global Token、Norm、SENet、任务头、初始化、标签和训练协议。

| 实验轴 | D | L | M | 主要问题 |
|---|---|---|---|---|
| 锚点 | 256 | 2 | 704 | 重跑基线及波动范围 |
| 深度 | 256 | 3、4 | 704 | 连续加深是否带来持续净收益 |
| 通道宽度 | 384、512 | 2 | 704 | 扩大 token 通道在固定 FFN 中间宽度下是否有效 |
| FFN 中间宽度 | 256 | 2 | 512、896 | 增益来自通道容量还是非线性中间空间 |

这个完整网格共 7 个唯一配置，不要求首批全部执行。多随机初始化的数量应按目标效应量与预算事先确定，3 次只能作为初步波动评估，不能视为统计保证；追加重复的规则也应预先写明，避免观察显著性后任意决定是否继续。实际优先点和配对对照采用 05 的近整模型等参方案。

当前主干双 SwiGLU 的主要矩阵参数为：

\[
 P_{backbone}\approx6LTDM\quad(H=T，逐token权重独立，忽略bias/norm)。
\]

因此 (L=2,D=384,M=704) 与 (L=3,D=256,M=704) 的主干矩阵量相等；(L=2,D=512) 与 (L=4,D=256) 也相等。**它们是有用的主干等参对照起点，但不是整模型等参对照**：token projection、Global projection、flatten 后首层任务头会随 D 变化。比较时须同时给出主干参数和整模型参数。

若要回答“同样总预算投向深度还是宽度更好”，另做总参数匹配版本，可调整 M 使整体预算接近（例如误差≤2%，并公开剩余差）；不要在已宣称的单变量实验中悄悄同时改任务头。实测 FLOPs 与 wall clock 仍应另列，等参不能替代等算力。

### 4.2 可选数据与诊断设计：区分训练不足、表示瓶颈和任务头瓶颈

从已完成的规模对照中挑 3 个有代表性的规模（小、中、大），分别增加同一截止日前可用训练样本量，并画学习曲线。推荐两条互补口径：

- **等数据/更新暴露**：所有模型使用同一批按时间排序的样本；观察扩大模型后最终指标和收敛速度。
- **等实际计算预算**：固定总 GPU 小时或经测量的训练 FLOPs；大模型允许处理的更新更少，比较同成本可达表现。

两条曲线回答不同问题，不应混画成一个结论。统计唯一样本数、重复曝光数、正例数、训练更新数、batch 和数据分布；同一旧数据多训几轮与引入更多独立新样本不是同一类 data scaling。

CVR 数据的扩大必须固定特征观察截止点与标签成熟窗；更长历史同时改变时效性和正例可用性。至少用多个共同测试日比较，并给出同日差值、用户聚类的重采样区间、校准指标和业务关注分层。所有超参数选择只能看训练/验证，最终测试日不参与挑选最优配置。

读出瓶颈可用同一主干 checkpoint 的诊断探针或端到端等预算读出消融检查。PureFlat、MeanPool、任务塔变深会改变读出信息量和参数分布，若与主干深度同时修改，不能把差值全部归给 L。

### 4.3 可选结构干预：按诊断结果决定结构修改

| 观察到的现象 | 优先假设 | 下一步能排除混杂的对照 |
|---|---|---|
| 大模型训练与验证都落后，延长训练后恢复 | 优化/数据暴露不足 | 同规模更长训练、同预算学习率与 warmup 小范围搜索 |
| 训练改善、验证恶化 | 泛化或数据时效问题 | 更多独立数据、固定规则正则、按频次/时间分层评估 |
| 新增 block 更新很小且下层梯度弱 | 残差/初始化/深层监督不匹配 | 固定 L，分别加入跨层残差或辅助监督，再扩深 |
| 某类输入 token 跨样本谱很窄 | 输入冗余或长尾集中 | 固定输入维度的语义/固定随机分组、多种分组 seed |
| 深层谱下降且预测同时饱和 | mixing/FFN 或读出丢失信息 | 等预算结构化 mixing；分开测 FFN、Norm、读出 |
| 效果能随 dense 扩张改善但服务成本过高 | 激活计算或系统实现限制 | 先测算子耗时，再做低精度/融合或稀疏化，分清总参数与激活参数 |

不建议一次把随机 token、多 embedding、Full Mixing、Task Token 和更深主干全部叠上去。这样即使有收益，也无法判断新增资源最值得投在哪里。

## 5. 资源口径与 scaling law 的最低证据要求

每个模型至少保存以下成本账本：稀疏 embedding 参数/字节；dense 总参数；每样本激活参数；主干/输入/读出参数分解；训练与推理每样本 FLOPs；batch；精度；硬件型号/数量；同步方式；端到端吞吐；p50/p95 延迟；峰值显存；完整训练 GPU 小时。需要明确 FLOPs 是否将一次乘加计为 2、是否含反向、embedding 和优化器；MFU 使用哪种精度的硬件峰值，以及统计的是主干还是全流程。

推荐分三张图而非一个“越大越好”的散点图：

1. 同结构同数据的 AUC/LogLoss 对 dense 参数，区分扩深/扩宽/扩 M。
2. AUC/LogLoss 对总训练 FLOPs 或 GPU 小时，展示实际预算内最优值。
3. 质量对推理 p95 延迟/吞吐，形成可部署的折中集合。

如果未来需要声称本项目存在可预测 scaling law，建议在固定结构族内至少取得 4-6 个覆盖充分的容量点，控制数据与调参预算，带重复与误差区间；比较简单基线、饱和模型和幂律拟合，并保留尚未参与拟合的更大规模点验证预测。点数只是设计建议，不是统计充分性的保证。

不建议先对 AUC 写无限增益幂律。更可检验的候选形式是某一固定训练协议下的验证损失 `loss(P)=loss_floor+a*P^(-alpha)`，再检查数据量与训练预算是否改变曲线；拟合的 loss_floor、alpha 存在较强耦合，未跨越足够规模范围时不能过度解读。只有同等任务质量下的成本下降或同等成本下的质量提高，才能支撑资源投入决策。
