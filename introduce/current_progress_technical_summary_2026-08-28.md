# 搜索首次转化率模型当前进度技术总结

> 总结日期：2026-08-28
>
> 任务：电商搜索候选排序的首次转化率（`fst_CVR`）预估
>
> 主指标：次日测试集 ROC-AUC
>
> 结论口径：`1 AUC bp = 0.0001 AUC`

## 1. 结论摘要

当前项目已经完成从 Base 复现、RankMixer v1–v9 结构迭代，到 UniMixer v1 和 RankMixer v10 候选方案实现的主体开发。结合现有训练记录和源码，当前结论如下。

1. **Base 仍是唯一经过多日验证且整体最优的方案。** 第一轮 15 天训练最终 AUC 为 `0.869715`；第二轮 6 天训练峰值为 `0.869868`。现有 RankMixer 版本均未形成稳定超过 Base 的证据。
2. **RankMixer 已明显缩小与 Base 的差距，但尚未完成替代。** 第一轮中，v1 四日平均落后 Base `26.75 bp`，v3 六日平均落后 `12.30 bp`，v5 三日平均落后 `7.00 bp`。第二轮首日中，v6 以 `0.866017`、落后 Base `9.43 bp`，是该轮已记录候选中最接近 Base 的版本。
3. **目前最可靠的 RankMixer 正向模块证据是“字段安全 + 业务语义分组”。** v1 的裸维度切分会破坏 17 维字段边界；v3 在与 v2 参数量、主干规模基本相同的情况下，仅将顺序分组升级为业务语义分组，首日提升 `3.01 bp`。
4. **单纯扩大模型容量没有带来稳定收益。** v5 固定 Dense 参数达到 `348.432M`，约为 Base 的 `3.86` 倍；它在第一轮最接近 Base，但第二轮首日差距扩大到 `27.97 bp`。v6 将主干宽度降到 512、参数减半后，第二轮首日反而比 v5 高 `18.54 bp`。由于 v5→v6 同时改变了分组和宽度，这一结果不能归因于单个因素。
5. **显式交叉仍是当前重点方向，但“有交叉”不等于“必然增益”。** Base 的全维 DCN-M 与整体领先同时出现；v4 的轻量 Query-Item Cross 相对 v3 下降 `2.82 bp`。v8/v9 因此改为在完整字段空间恢复更强的交叉，再与 TokenMixer 融合，但尚缺少可确认的多日训练证据。
6. **当前主要瓶颈已经从“缺少新结构”转向“实验可复现性和归因能力不足”。** 现有结果缺少固定随机种子、逐样本预测、配对置信区间和生产图性能数据；部分运行参数与实验记录存在漂移。继续增加版本的边际价值低于先把当前候选做公平、多 seed、多日验证。

因此，项目当前应定位为：**架构探索基本完成，进入候选收敛、实验审计和严格验证阶段；尚未达到模型晋级或线上替换条件。**

## 3. 任务、输入与统一实验协议

### 3.1 任务和输入

模型只预测搜索候选曝光后的首次转化概率，主标签为 `fst_cvr_label`。所有公平对比使用相同三桶特征：

| 特征桶 | 字段数 | 单字段 Embedding | 展平维度 |
|---|---:|---:|---:|
| `common` | 385 | 17 | 6,545 |
| `item` | 835 | 17 | 14,195 |
| `creative` | 14 | 17 | 238 |
| **合计** | **1,234** | **17** | **20,978** |

所有 RankMixer 和当前 UniMixer 候选均不应增加 coupon、sequence、DIN、gattr 或其他新特征。这样可以把效果变化主要归因于 Dense 主塔，而不是输入数据变化。

### 3.2 训练链

仓库记录了两条互相独立的实验链：

- 第一轮起点：`2026-07-01`
- 第二轮起点：`2026-08-15`

统一协议为：

1. 起始日约 5.5 亿训练样本，第二天约 1.1 亿测试样本。
2. 起始日 Sparse Embedding 按公共来源热启动，全部 Dense 参数随机冷启动。
3. 后续日期只能加载同一模型前一天的 Dense checkpoint，不允许跨模型、跨实验轮次热启动。
4. 每天训练完成后在第二天相同测试数据上比较 `fst_CVR` AUC。
5. Base 与候选模型必须使用相同数据、过滤、步数和评估口径。

这一协议本身是正确的，但 `auto_load_cp=true` 与历史输出目录并存时仍可能误载旧 Dense checkpoint，因此“空输出目录 + checkpoint 清单”必须作为实际运行前置检查，而不能只依赖 `ignore_dense_checkpoint=True`。

## 4. 技术路线演进

当前架构关系可概括为：

```text
Base：三桶 BN → Hierarchical SENet → 2×DCN-M500 → 深 MLP

v1 → v2 → v3 → v4
          └────→ v7（只验证深任务头）

v5 → v6 → v8 → v9（重新锚定 Base 的显式交叉）
      └────────→ v10（LayerNorm + PureFlat，开发中）

UniMixer v1：独立的可学习双随机 Mixing 路线
```

### 4.1 Base：当前强基线

Base 的有效主路径为：

```text
20,978 维三桶输入
→ 三桶 BatchNorm
→ 分层 SENet 字段门控
→ 两层全维 DCN-M（rank=500）
→ 2048→2048→256 深任务头
→ fst_CVR
```

其优势是保留完整字段坐标，在压缩前进行全维显式乘性交互，并用深任务头完成最终映射。现有结果只证明这套组合整体有效，不能把领先幅度分别归因给 SENet、DCN-M 或深头中的某一个模块。

### 4.2 v1–v4：先修复 Token 化，再验证轻量搜索交互

| 版本 | 主要变化 | 代码与实验含义 |
|---|---|---|
| v1 | 20,978 维输入按裸维度切成 16 Token，`D=768`、PFFN `k=4` | 切分点不按 17 维字段对齐，会切断字段并产生跨桶 Token；连续四日明显落后 Base |
| v2 | 字段安全分组、恢复 SENet、PFFN `k=2`、Gated Pool、Bucket Cross、学习率里程碑 reset | 相对 v1 首日提升 `6.57 bp`，但同时变化项目太多，只能判定整套修复净正向 |
| v3 | 将 v2 的桶内顺序均分改为 16 个固定业务语义组 | 参数量和主 FLOPs 与 v2 相同，首日提升 `3.01 bp`，是当前最清晰的单模块正向证据 |
| v4 | 在 v3 上增加两条低秩 Query→Item Cross | 首日相对 v3 下降 `2.82 bp`；只否定当前实现，不否定 Query-Item 交互类别 |

### 4.3 v5–v9：增强容量、读出和显式交叉

| 版本 | 核心结构 | 当前定位 |
|---|---|---|
| v5 | 31 Local + 1 Global Token，`D=1024`，两层双空间 Per-token SwiGLU，Global-conditioned Pool + Flatten + 深头 | 第一轮最接近 Base，但参数和计算最大；第二轮首日出现明显异常 |
| v6 | v5 型主干改为语义均衡分组，`D=512`，其余主要结构保留 | 参数较 v5 减少 49.14%；第二轮首日是已记录候选中最好，但只有单日结果 |
| v7 | 完整保留 v3 主干，仅将线性输出替换为 `2048→2048→256` 深任务头 | 是隔离“任务头容量”影响的干净候选；尚无训练 AUC 记录 |
| v8 | v6 前增加两层 Masked Low-Rank DCN，交叉视图形成 Local Token，原始视图形成 Global Token | 目标是在语义压缩前恢复显式交叉；已有代码与参数约束，尚无训练 AUC 记录 |
| v9 | 精确复用 Base 两层 DCN-M500，构造 Raw/Cross 双视图 Token，并增加 512 维 DCNM Shortcut | 当前主候选；固定参数小于 200M，静态契约测试完备，但训练结果归属存在文档冲突 |

v9 的完整路径为：

```text
三桶 BN → Hierarchical SENet
→ Base 同构 2×DCN-M500
→ Raw/Cross 双视图 31 个 Local Token + Cross Global Token
→ 2×TokenMixer-Large
→ Global + Conditioned Pool + Gated Flatten + DCNM Shortcut
→ 2048→2048→256 深任务头
→ fst_CVR
```

这一设计反映了当前最重要的架构判断：TokenMixer 不再完全替代 Base 的显式交叉，而是作为 DCN-M 后的增量表示模块。

### 4.4 v10：静态实现就绪的 PureFlat 候选

截至本次核查，工作区新增了 [`cvr_bn_rankmixer_v10.py`](../src/models/rankmixer/cvr_bn_rankmixer_v10.py)、[`set-rankmixer-v10-args.txt`](../bash/set-rankmixer-v10-args.txt)、[`rankmixer_v10_introduction.md`](rankmixer_v10_introduction.md) 和 [`test_rankmixer_v10_static.py`](../src/models/rankmixer/tests/test_rankmixer_v10_static.py)。这些文件尚未纳入版本控制，也没有训练结果，但代码、参数、说明和静态测试已经形成闭环。

当前代码快照以 v6 的 31+1 语义 Token、`D=512`、`M=704` 双 SwiGLU 主干为基础，做了两项主要改变：

1. Token 投影后、Block PreNorm 和最终归一化统一改为标准 LayerNorm。
2. 删除 Global-conditioned Pool、压缩 Flatten 和 scalar gate，直接把 `[B,32,512]` 展平为 `[B,16,384]`，进入 `2048→2048→256` 单路径任务头。

按当前代码逐模块复算，固定 Dense 参数为 **199,275,877（199.276M）**，扩展前向 FLOPs 为 **399,355,903（0.399356G）**；字段覆盖为 `385/835/14`，三桶字段顺序 checksum 与 v6/v8/v9 一致。当前只能把 v10 视为“静态实现就绪的研发候选”，不能纳入效果排名。

### 4.5 UniMixer v1：独立可学习 Mixing 路线

[`cvr_bn_unimixer_v1.py`](../src/models/rankmixer/cvr_bn_unimixer_v1.py) 使用 32 个互斥语义 Token（10 common + 21 item + 1 creative），每个 Token 512 维；在两层 UniMixing-Lite 中学习低秩、近双随机的局部/全局混合矩阵，并配合 Pertoken SwiGLU、SiameseNorm 和展平深任务头。

固定 Dense 参数约 **150.758M**。代码、参数文件和说明文档已经完成，字段完整覆盖和单文件运行契约已有静态测试；尚无服务器建图或测试 AUC，因此当前状态是“静态就绪、训练未验证”。

### 5.3 v9 结果的归属冲突

`background.md` 第 5.9.2 节记录 v9 在 `2026-08-15` 冷启动后的 AUC 为 `0.865254`，但同一文件第 6.1 节及 [`rankmixer_v9_introduction.md`](rankmixer_v9_introduction.md) 又写明当前 v9-Small 尚未在生产环境训练。

在缺少运行 manifest、模型文件 hash 和 checkpoint 元数据的情况下，无法确认该 AUC 对应：

- 当前 `cvr_bn_rankmixer_v9.py`；
- v9 的早期 Base-Anchored 方案；
- 或另一份服务器侧代码。

因此本文保留该数值作为“已记录结果”，但不把它作为当前 v9-Small 的已验证效果。该问题应在下一次训练前优先解决。

## 7. 当前已获得的技术认识

### 7.1 可以相对确定的结论

1. **字段边界必须保持。** 当前输入的最小语义单位是 17 维字段 Embedding，v1 的裸切分结构上不适配这一数据契约。
2. **固定业务语义 Token 优于机械顺序分组。** v3 对 v2 是现有归因最清晰的相邻版本对照，方向为正。
3. **Base 的完整显式交叉路径很强。** Base 的持续领先证明其整体主塔适配当前任务；这为 v8/v9 重新引入全维交叉提供了合理依据。
4. **大容量不是当前核心缺口。** v5 已经证明模型可以大幅增容并提高训练拟合，但没有证明更强泛化，第二轮还暴露出明显稳定性问题。
5. **任务头值得单独验证。** v7 基本只替换 v3 的输出头，是少数可以形成明确归因的候选，不应被更多同时变化的版本跳过。

### 7.2 当前仍不能确定的结论

1. 不能把 Base 的领先单独归因给 SENet、DCN-M 或深 MLP。
2. 不能从 v2 对 v1 的提升中拆出字段安全、SENet、Gated Pool、Bucket Cross、`k=2` 或学习率 reset 各自贡献。
3. 不能把 v6 对 v5 的单日领先归因给语义分组或降维，因为两项同时变化。
4. 不能依据 v4 判断所有 Query-Item 交互无效，只能判断当前两条低秩末端残差实现没有净收益。
5. 不能依据记录中的 v9 单日结果判断当前 v9-Small 无效，必须先确认结果归属并进行多 seed 复现。
6. 不能把静态参数量和 FLOPs 直接等价为生产训练速度或在线延迟。

- v8/v9/v10 在构造期加入固定 Dense 参数预算检查；v9 还验证了生产变量 scope、Raw/Cross 融合和上下文维度，v10 验证了标准 LayerNorm、PureFlat 单路径和实际建图参数预算。
- v9、v10 与 UniMixer v1 共 **25 个静态测试**已在当前本地环境全部通过：v9 6 个、v10 8 个、UniMixer v1 11 个。

### 8.2 尚未完成

- v7、v8、当前 v9-Small、v10、UniMixer v1 均缺少明确可归属的完整服务器训练记录。
- 本地缺少生产 TensorFlow 1.x、Flood 与 Cayman 环境，无法完成真实建图、单步前后向、导出和 profiler 验证。
- v10 的代码、参数、介绍和测试尚未提交，也未在生产环境完成建图、训练或导出验证。
- 没有自动化实验登记表将“代码提交、参数文件、数据日期、checkpoint、随机种子、输出目录和 AUC”绑定在一起。

## 9. 主要风险与待排查问题

### P0：会直接影响实验结论

1. **v9 结果归属冲突。** 在确认代码 hash 和运行任务前，不能把 `0.865254` 当作当前 v9-Small 的正式结论。
2. **v5 第二轮冷启动异常。** 两轮首日相对 Base 的差距从 `-7.91 bp` 扩大到 `-27.97 bp`，应先核查 Dense 是否真正冷启动、Sparse 来源、样本、代码、参数、训练步数和运行环境。
3. **运行脚本与实验日期漂移。** 多个 args 文件仍写 `2026-07-01`，不能直接代表第二轮实际任务；v3 参数中还存在 `hhdfs://` 拼写。服务器运行参数必须从真实任务保存，而不是事后根据模板推测。
4. **`auto_load_cp` 误续训风险。** 即使设置 `ignore_dense_checkpoint=True`，已有模型输出目录仍可能触发本方案自己的旧 checkpoint 自动加载。
5. **缺少固定 seed 和重复实验。** 3–10 bp 级差异可能混入初始化波动；当前大部分相邻版本只有一次冷启动。

### P1：限制模块归因和效果可信度

1. AUC 使用 `num_thresholds=2000` 的流式近似，仓库没有 exact AUC、逐样本预测和配对置信区间。
2. 不同日期样本存在分布漂移，同一 `search_id`/用户下样本也不独立；简单比较日均值不能替代成组显著性检验。
3. 部分配置虽然被读取，但主优化路径没有明确应用，例如某些版本中的 Dropout、梯度裁剪和正则项；不能把这些参数当作已生效控制变量。
4. 当前版本改动经常同时包含多个模块，v5→v6、v8→v9、v6→v10 都不足以直接做单模块因果归因。

### P2：工程部署风险

1. 静态 FLOPs 未包含 transpose/concat 内存开销、稀疏参数服务器通信和反向计算。
2. v5–v10 的 Token-specific SwiGLU 参数量和中间激活较大，需要实际记录吞吐、峰值显存/内存和在线 P99 延迟。
3. 字段列表和 Token 顺序已经成为模型 ABI；任何字段增删、重排或语义组调整都必须升级版本并重新冷启动 Dense 参数。

## 10. 推荐的下一阶段计划

### 10.1 先建立可复现实验底座

每次训练必须自动保存一份不可变 manifest，至少包含：

```text
模型文件 SHA256 / Git commit
参数文件 SHA256 与完整展开参数
训练、测试日期和样本版本
Sparse checkpoint 来源
Dense 启动方式与实际恢复变量清单
模型输出目录及训练前是否为空
随机种子、训练步数、worker/PS 配置
Dense 参数量、代码分组版本与字段 checksum
最终 checkpoint、逐样本预测路径和评估结果
```

这一步完成后，v9 的结果归属、v5 的冷启动异常和后续所有版本的可复现性才能得到根本解决。

### 10.2 第一优先级实验

1. 在完全相同的 `2026-08-15` 数据和 Sparse checkpoint 上，对 Base、v5、v6、当前 v9-Small 各做至少 3 个固定 seed 冷启动。
2. 先确认 v5 的异常是否可复现；若不可复现，排查任务配置或 checkpoint 污染；若稳定复现，再讨论日期分布效应。
3. 对 v6 和确认后的 v9 至少继续 3 个训练日，只沿同版本 checkpoint 热启动，观察差距是收敛、稳定还是扩大。
4. 保存所有模型的逐样本 `search_id/example_id/label/pred`，计算 exact ROC-AUC、GAUC、COPC/校准误差，并以 `search_id` 或用户为 block 做 paired bootstrap。

### 10.3 第二优先级消融

| 对照 | 目标 |
|---|---|
| v3 vs v7 | 单独验证深任务头是否弥补 RankMixer context 的非线性映射不足 |
| v5 vs “仅语义分组” vs “仅 512 维” vs v6 | 分离语义分组和降维的贡献 |
| v6 vs LayerNorm-only vs PureFlat-only vs v10 | 分离归一化与读出简化的贡献；不要只比较同时改变两项的 v10 |
| v8 Mask on/off | 判断动态 Mask 是否优于普通 Low-Rank DCN |
| v9 Shortcut on/off、Raw/Cross 双视图消融 | 判断 Base 锚定路径和不同视图的独立价值 |
| UniMixer v1 Token-BN on/off | 在主结构有效后再验证投影后独立 BN 的贡献 |

### 10.4 晋级条件建议

候选方案至少满足以下条件后再进入线上评估：

1. 多 seed、多日平均 AUC 不低于 Base，且 paired block bootstrap 的差值置信区间不跨越预先约定的负向阈值。
2. Query 长短、冷启动商品、价格段、用户活跃度、召回源等关键切片无明显退化。
3. COPC、分桶校准和业务请求级排序指标不退化。
4. 训练吞吐、资源占用、导出稳定性和线上 P99 延迟满足工程预算。
5. 代码、参数、字段 ABI、checkpoint 和评估产物可由 manifest 完整复现。

## 11. 最终判断

当前项目最有价值的进展不是某个新版本已经超过 Base，而是已经逐步明确了问题边界：

- v1 证明裸维度 Token 化不适配字段结构；
- v2/v3 证明字段安全和业务语义组织是正确方向；
- v4 说明轻量末端 QI 残差不足以解决显式交互；
- v5/v6 说明容量扩大不是充分条件，语义组织和优化难度同样关键；
- v8/v9 开始将 Base 的显式交叉优势与 TokenMixer 的隐式交互结合；
- v7、v10 和 UniMixer v1 提供了任务头、归一化/读出和可学习 Mixing 的可控后续候选。

截至 2026-08-28，**Base 仍应作为生产与离线评估基准；v6 是已有第二轮记录中最值得继续多日复现的 RankMixer；当前 v9-Small 是结构上最完整但必须先确认训练归属的主候选；v10 和 UniMixer v1 仍属于待建图、待训练的研发方案。** 下一阶段的最高优先级应是冻结实验口径、补齐多 seed 和逐样本统计，而不是继续无约束增加模型版本。
